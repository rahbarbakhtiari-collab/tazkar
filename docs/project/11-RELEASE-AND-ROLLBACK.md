## ۱. هدف

این سند فرایند ساخت نسخه، استقرار، انتشار مرحله‌ای، پایش، بازگشت نرم‌افزار و بازگردانی محتوای واردشده را تعیین می‌کند.

دو مفهوم مستقل‌اند:

1. **Release rollback:** بازگشت از نسخه افزونه جدید به نسخه پیشین؛
2. **Import rollback:** بازگردانی محتواهای متعلق به یک بسته ورود.

---

## ۲. کانال‌های انتشار

### Development Build

- مخصوص توسعه؛
- ممکن است ناپایدار باشد؛
- نباید در سایت اصلی نصب شود.

### Internal Alpha

- نصب روی staging؛
- داده ساختگی یا محدود؛
- فقط تیم پروژه.

### Closed Beta

- محتوای واقعی تأییدشده؛
- کاربران منتخب دانشگاهی؛
- بدون انتشار عمومی مخزن.

### Release Candidate

- feature freeze؛
- فقط رفع خطا؛
- بسته مشابه نسخه نهایی؛
- اجرای آزمون کامل و Go/No-Go.

### Stable

- استقرار کنترل‌شده روی سایت اصلی؛
- سپس انتشار عمومی در صورت پایداری.

## ۳. نسخه‌بندی

الگوی SemVer:

```text
MAJOR.MINOR.PATCH
```

نمونه‌ها:

- `0.1.0`: alpha؛
- `0.5.0`: beta؛
- `0.9.0`: release candidate؛
- `1.0.0`: نخستین stable؛
- `1.0.1`: رفع خطا؛
- `1.1.0`: قابلیت سازگار جدید؛
- `2.0.0`: تغییر ناسازگار.

نسخه‌های pre-release:

```text
1.0.0-beta.1
1.0.0-rc.1
```

نسخه plugin header، constant، package، tag و changelog باید یکسان باشند.

## ۴. مدیریت کد

پیشنهاد:

- `main`: نسخه پایدار یا آماده انتشار؛
- branchهای کوتاه برای feature و fix؛
- Pull Request برای ادغام؛
- tag نسخه برای artifact نهایی؛
- CI اجباری پیش از merge.

در تیم تک‌نفره نیز checklist، test و ثبت تصمیم جای review همکار را تا حد ممکن جبران می‌کند.

## ۵. artifact انتشار

بسته ZIP نسخه نهایی از source repository ساخته و پس از تأیید تغییرناپذیر تلقی می‌شود.

### شامل

- کد PHP؛
- assetهای build؛
- dependencyهای runtime پیشوندگذاری‌شده؛
- templateها؛
- `readme.txt`؛
- مجوزها و noticeها؛
- فایل POT؛
- `uninstall.php`.

### فاقد

- `.env` و secret؛
- log و cache؛
- `node_modules`؛
- dependencyهای توسعه؛
- fixtureهای حجیم؛
- فایل‌های شخصی؛
- فونت بدون مجوز؛
- کتاب یا منبع دارای محدودیت انتشار.

---

## ۶. ساخت قابل بازتولید

برای هر release ثبت می‌شود:

- tag و commit hash؛
- نسخه ابزارهای PHP و Node؛
- lockfileها؛
- دستور build؛
- checksum ZIP؛
- زمان و اجراکننده.

artifact منتشرشده باید از tag ثبت‌شده قابل بازسازی باشد.

---

## ۷. مجوز و آمادگی مخزن

مجوز پیشنهادی Core:

```text
GPL-2.0-or-later
```

افزونه برای WordPress.org باید:

- محصولی کامل و production-ready باشد؛
- با دستورالعمل‌های مخزن سازگار باشد؛
- source قابل بررسی داشته باشد؛
- `readme.txt` معتبر داشته باشد؛
- `Stable Tag` عددی داشته باشد؛
- `Tested up to` فقط نسخه واقعاً آزموده‌شده باشد؛
- Plugin Check را بدون خطای مانع اجرا کرده باشد؛
- تماس خارجی پنهان نداشته باشد؛
- همه dependencyها و assetها مجوز سازگار داشته باشند.

---

## ۸. Git و SVN وردپرس

Git مرجع توسعه است و SVN مخزن WordPress.org فقط برای release استفاده می‌شود.

ساختار SVN:

```text
trunk/
tags/1.0.0/
assets/
```

قواعد:

- artifact تأییدشده به SVN منتقل می‌شود.
- نسخه در `tags/<version>` ثبت می‌شود.
- `Stable Tag` به نسخه عددی اشاره می‌کند.
- از `trunk` به‌عنوان Stable Tag استفاده نمی‌شود.
- assetهای صفحه مخزن از ZIP افزونه جدا هستند.

## ۱۲. چک‌لیست Go/No-Go

### محتوا

- [ ] بسته اولیه تأیید شده است.
- [ ] متن عربی تطبیق داده شده است.
- [ ] محتوای تأییدنشده عمومی نیست.

### فنی

- [ ] CI سبز است.
- [ ] migration و upgrade پاس شده‌اند.
- [ ] import، resume و rollback پاس شده‌اند.
- [ ] REST و privacy پاس شده‌اند.
- [ ] backup و restore آزموده شده‌اند.

### بسته

- [ ] نسخه‌ها هماهنگ‌اند.
- [ ] checksum ثبت شده است.
- [ ] secret و فایل توسعه وجود ندارد.
- [ ] مجوزها کامل‌اند.
- [ ] readme و changelog معتبرند.

### تصمیم

- [ ] مدیر پروژه Go را ثبت کرده است.

## ۱۶. trigger بازگشت نرم‌افزار

بازگشت فوری بررسی می‌شود اگر:

- fatal گسترده رخ دهد؛
- داده از دست برود یا فاسد شود؛
- آسیب‌پذیری فعال کشف شود؛
- محتوای تأییدنشده منتشر شود؛
- migration شکست بخورد؛
- rollback محتوا خارج از scope اثر بگذارد؛
- frontend به‌طور شدید مختل شود؛
- مصرف منابع غیرعادی شود.

برای خطای محدود با patch سریع، forward fix می‌تواند مناسب‌تر باشد.

---

## ۱۷. روش بازگشت نرم‌افزار

### بدون migration ناسازگار

1. توقف import و انتشار گروهی؛
2. backup وضعیت فعلی؛
3. نصب نسخه قبلی؛
4. پاک‌سازی cache؛
5. smoke test؛
6. ثبت incident.

### با migration ناسازگار

1. maintenance؛
2. توقف write؛
3. restore database یا migration معکوس آزموده‌شده؛
4. نصب نسخه قبلی؛
5. بررسی schema؛
6. smoke test؛
7. بازگشایی کنترل‌شده.

بازگشت کد بدون بازگردانی schema در تغییر ناسازگار ممنوع است.

---

## ۱۸. Forward Fix

اگر داده سالم و مشکل محدود باشد:

- branch hotfix؛
- آزمون متمرکز و regression؛
- نسخه PATCH؛
- artifact و checksum جدید؛
- استقرار کنترل‌شده؛
- ثبت علت و پیشگیری.

---

## ۱۹. بازگردانی بسته محتوا

فرایند مستقل:

1. انتخاب batch؛
2. preview؛
3. نمایش draft، publish، edited و interaction؛
4. تأیید مدیر؛
5. انتقال پیش‌فرض به Trash؛
6. ثبت نتیجه ردیف‌ها؛
7. بررسی sitemap و لینک‌ها؛
8. امکان restore از Trash.

موارد منتشرشده یا ویرایش‌شده هشدار جدا دارند.

---

## ۲۰. مدیریت migration

هر migration باید دارای این اطلاعات باشد:

- شماره نسخه؛
- پیش‌شرط؛
- تغییر schema یا داده؛
- آزمون upgrade؛
- روش rollback یا توضیح عدم امکان؛
- نیاز backup؛
- idempotency؛
- برنامه timeout.

migration طولانی در frontend اجرا نمی‌شود و در صورت نیاز chunk می‌شود.

---

## ۲۱. سازگاری عقب‌رو

برای PATCH و MINOR:

- API عمومی شکسته نشود.
- meta key بدون migration حذف نشود.
- hook عمومی ناگهانی حذف نشود.
- قرارداد داده 1.x پشتیبانی شود.
- template override با notice مناسب حفظ شود.

تغییر ناسازگار فقط در MAJOR و همراه مسیر مهاجرت مجاز است.

---

## ۲۲. Deprecation

- حداقل یک نسخه MINOR هشدار؛
- معرفی جایگزین؛
- استفاده از سازوکار deprecated وردپرس؛
- حذف در MAJOR بعدی؛
- حفظ کنترل امنیتی در API منسوخ تا حذف.

## ۲۴. انتشار امنیتی

- جزئیات قابل سوءاستفاده قبل از patch عمومی نمی‌شود.

- changelog توضیح کافی ولی ایمن دارد.
- در صورت لزوم هماهنگی با تیم افزونه‌های WordPress.org انجام می‌شود.
