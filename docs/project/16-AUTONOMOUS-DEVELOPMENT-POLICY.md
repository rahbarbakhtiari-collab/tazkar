## ۱. تصمیم اصلی

تست انسانی و تأیید انسانی از Sprintها، Pull Requestها، buildهای شبانه و نسخه‌های میانی حذف می‌شود.

انسان فقط در این موارد وارد فرایند می‌شود:

1. تصمیمی که در اسناد مصوب پاسخ ندارد؛
2. تغییر هدف، دامنه یا قرارداد اصلی محصول؛
3. تغییر سیاست امنیت، حریم خصوصی، درآمد یا تماس خارجی؛
4. تصمیم علمی و شرعی نهایی درباره محتوا؛
5. دسترسی، credential یا هزینه‌ای که ابزارها اختیار آن را ندارند؛
6. وضعیت `BLOCKED` پس از پایان سقف اصلاح خودکار؛
7. آزمون پذیرش نهایی Release Candidate و تصمیم انتشار Stable.

## ۲. اصل منبع حقیقت

- GitHub منبع حقیقت کد، Issue، PR، CI، artifact و release است.
- اسناد فعال پروژه، معیار تصمیم عامل‌ها هستند.
- خروجی شفاهی عامل بدون commit، PR، check یا artifact معتبر نیست.
- شاخه `main` باید همیشه قابل ساخت و قابل نصب باشد.

## ۳. چرخه خودکار هر Task

```text
Issue با برچسب agent-ready
        ↓
عامل برنامه‌ریز: دامنه و معیار پذیرش
        ↓
عامل پیاده‌ساز: branch + code + tests
        ↓
CI: lint/static/unit/integration/security/build
        ↓
عامل‌های بازبین مستقل
        ↓
FAIL؟ ── بله → عامل تعمیر CI، حداکثر ۳ دور
  │
  خیر
  ↓
Auto-merge برای PR مجاز
        ↓
Nightly build و آزمون regression
```

## ۴. وضعیت‌های مجاز

هر کار فقط یکی از این وضعیت‌ها را دارد:

- `READY`: مشخصات کامل و قابل اجرا؛
- `IN_PROGRESS`: عامل در حال اجرا؛
- `REVIEW`: کد آماده و دروازه‌ها در حال بررسی؛
- `REPAIR`: عامل در حال رفع خطا؛
- `PASS`: همه دروازه‌ها سبز؛
- `BLOCKED`: تصمیم یا دسترسی بیرون از اختیار ابزار لازم است؛
- `MERGED`: روی main ادغام شده؛
- `RC_REQUIRED`: فقط در Release Candidate به پذیرش انسانی نیاز دارد.

## ۵. سقف حلقه اصلاح

- هر خطای CI حداکثر سه دور اصلاح خودکار دارد.
- پس از سه شکست با علت یکسان، Issue با وضعیت `BLOCKED` ایجاد یا به‌روزرسانی می‌شود.
- عامل باید شواهد خطا، فرمان‌های اجراشده و آخرین فرضیه را ثبت کند.
- تکرار بی‌پایان یا تغییر بی‌قاعده آزمون برای سبزکردن CI ممنوع است.

## ۶. استقلال بازبینی

عامل پیاده‌ساز، تأییدکننده نهایی تغییر خود نیست.

حداقل در تغییرهای پرخطر:

```text
Test Gate       PASS
Architecture    PASS
Security        PASS
```

بازبین‌ها باید diff و شواهد تست را بررسی کنند، نه فقط خلاصه عامل پیاده‌ساز را.

## ۷. طبقه‌بندی ریسک

### کم‌خطر

- مستندات فنی بدون تغییر تصمیم محصول؛
- تست جدید؛
- refactor بدون تغییر رفتار؛
- اصلاح lint و CI؛
- بهبود پیام و گزارش داخلی.

قابل auto-merge پس از سبزشدن checkهای اجباری.

### متوسط

- قابلیت جدید در محدوده مصوب Sprint؛
- تغییر UI بدون تغییر قرارداد؛
- تغییر validator با تست کامل؛
- query یا performance optimization.

قابل auto-merge پس از CI و بازبینی مستقل عامل.

### پرخطر

- migration؛
- import و فایل ورودی؛
- capability، nonce، REST، privacy و حذف داده؛
- dependency runtime؛
- release build؛
- تغییر مسیر نگهداری داده.

نیازمند سه دروازه مستقل ماشینی است، ولی تست انسانی میانی ندارد.

### نیازمند انسان

- تغییر منشور، MVP، قرارداد داده یا تصمیم حاکم؛
- تصمیم شرعی یا صحت علمی محتوا؛
- تماس خارجی یا سیاست داده جدید؛
- انتشار Stable.

## ۸. سیاست merge

Auto-merge فقط وقتی مجاز است که:

- branch با `agent/` آغاز شود؛
- PR از همان repository باشد؛
- PR Draft نباشد؛
- برچسب `automerge` داشته باشد؛
- برچسب `human-decision-required` یا `blocked` نداشته باشد؛
- تمام checkهای اجباری سبز باشند؛
- PR template کامل باشد؛
- فایل حاکم محافظت‌شده بدون مجوز تغییر نکرده باشد.

## ۹. تست انسانی نهایی

تست انسانی فقط روی ZIP دقیق Release Candidate انجام می‌شود، نه checkout دلخواه.

پذیرش نهایی شامل:

- نصب روی Local؛
- گردش کامل MVP؛
- بررسی بصری و روانی رابط؛
- آزمون محتوای نمونه؛
- بررسی رفتار واقعی کاربر؛
- تأیید علمی نمونه‌های دینی؛
- تصمیم انتشار یا بازگشت به توسعه.

## ۱۰. مرز خودکارسازی محتوای دینی

توسعه نرم‌افزار می‌تواند تا RC خودکار باشد؛ اما AI هیچ محتوای دینی را `approved` نمی‌کند. تأیید علمی نهایی محتوا همچنان انسانی است و می‌تواند در آزمون پذیرش RC یا فرایند تحریریه انجام شود.
