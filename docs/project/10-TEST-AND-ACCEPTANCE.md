## ۱. هدف

این سند روش اثبات صحت، امنیت، کیفیت محتوایی، دسترس‌پذیری و آمادگی انتشار MVP تذکار را تعیین می‌کند.

اصل آزمون:

> هیچ قابلیت صرفاً به‌دلیل کارکردن در محیط توسعه پذیرفته نمی‌شود؛ هر قابلیت باید معیار پذیرش، داده آزمون، نتیجه ثبت‌شدنی و روش بازتولید داشته باشد.

---

## ۲. اهداف کیفیت

MVP باید اثبات کند که:

1. متن عربی از فایل ورودی تا پایگاه داده، HTML و API بدون تغییر ناخواسته باقی می‌ماند.
2. داده ناقص یا ناسازگار پیش از ورود شناسایی می‌شود.
3. ورود نیمه‌تمام قابل ادامه یا بازگردانی است.
4. محتوای تأییدنشده در وب یا API عمومی ظاهر نمی‌شود.
5. طراحی در موبایل، دسکتاپ، RTL، LTR، حالت روشن و تیره پایدار است.
6. عملیات مدیریتی فقط با capability و کنترل CSRF معتبر انجام می‌شود.
7. داده‌های شخصی قابل export و erase هستند.
8. بسته انتشار فاقد secret، فایل توسعه و asset بدون مجوز است.
9. یک چرخه واقعی از Google Sheets تا انتشار کامل می‌شود.

## ۶. داده‌های مرجع آزمون

### معتبر

- قرآن کامل و قطعه جزئی؛

### نامعتبر

- حدیث بدون گوینده؛

- سلول شروع‌شونده با `=`, `+`, `-`, `@`؛
- فایل MIME ناسازگار؛

### تکرار

- ردیف کاملاً یکسان؛
- آیه یکسان با slug متفاوت؛

## ۸. آزمون حفاظت متن عربی

روش:

1. hash ورودی ثبت شود.
2. متن ذخیره‌شده از database خوانده شود.
3. مقدار API و HTML بررسی شود.
4. تطابق دقیق Unicode انجام شود.
5. تغییر عمدی پس از تأیید آزموده شود.

معیار پذیرش:

- مقدار ذخیره‌شده با ورودی برابر باشد.
- نرمال‌سازی تکرار در فیلد اصلی نوشته نشود.
- escape نمایشی مقدار ذخیره‌شده را تغییر ندهد.
- تغییر پس از تأیید، وضعیت را به `needs_recheck` ببرد.

هر عدم تطابق متن عربی یک **Release Blocker** است.

## ۹. آزمون CSV و XLSX

### CSV

- UTF-8 با BOM و بدون BOM؛
- متن دارای ویرگول و quote؛
- خط جدید در سلول؛
- ردیف خالی؛
- جداکننده نادرست؛
- formula injection؛
- فایل در حد مجاز و بیش از سقف.

### XLSX

- یک یا چند sheet؛
- Text و Number؛
- فرمول و لینک خارجی؛
- فایل رمزگذاری‌شده؛
- archive مشکوک؛
- ۵۰۰ ردیف؛
- فایل بیش از سقف.

معیار پذیرش:

- فرمول، object و macro اجرا نشود.
- فایل نامعتبر پیش از ایجاد post رد شود.
- نتیجه CSV و XLSX برای داده یکسان، از نظر محتوایی برابر باشد.

## ۱۰. آزمون import chunked

### سناریوی پایه

- فایل ۱۵۰ ردیفی؛
- chunk برابر ۲۵؛
- شش مرحله پردازش؛
- ثبت cursor پس از هر مرحله؛
- گزارش نهایی برابر مجموع ردیف‌ها.

### قطع عملیات

بعد از chunk سوم اتصال قطع شود.

انتظار:

- وضعیت batch و cursor حفظ شود؛
- ادامه از موقعیت درست انجام شود؛
- post تکراری ساخته نشود.

### شکست یک ردیف

- سایر ردیف‌ها ادامه یابند؛
- همان ردیف `error` شود؛
- وضعیت batch ناشناخته باقی نماند.

## ۱۱. آزمون تشخیص تکرار

- قرآن با سوره، آیه و متن یکسان: تکرار قطعی؛
- حدیث با متن نرمال‌شده، گوینده و مأخذ یکسان: تکرار قطعی؛
- شباهت زیاد یا کامل/جزئی: تکرار احتمالی.

معیار پذیرش:

- تکرار قطعی پیش‌فرض وارد نشود.
- override با دلیل ثبت‌شده ممکن باشد.
- اجرای دوباره همان فایل با checksum یکسان هشدار دهد.

## ۱۲. آزمون بازبینی و تأیید

- `low` و `critical_issue=yes` در تأیید گروهی مجاز نباشند.
- نمونه‌برداری قبل از اقدام گروهی الزامی باشد.
- اندازه نمونه مطابق قاعده ۱۰ ردیف یا ۱۰ درصد، با سقف ۳۰ باشد.
- ثبت یک خطای بحرانی، تأیید گروهی را متوقف کند.
- تأیید، خودکار publish نکند.
- تغییر فیلد حساس، بازبینی مجدد ایجاد کند.

## ۱۳. آزمون rollback بسته

حالت‌ها:

- فقط draft؛
- دارای published؛
- دارای post ویرایش‌شده؛
- دارای feedback یا favorite؛
- batch نیمه‌تمام؛
- اجرای دوباره rollback.

معیار پذیرش:

- فقط همان batch تحت تأثیر باشد.
- پیش‌فرض انتقال به Trash باشد.
- موارد منتشرشده و ویرایش‌شده هشدار جدا داشته باشند.
- اجرای دوم idempotent یا دارای پیام روشن باشد.
- نتیجه هر ردیف ثبت شود.

## ۱۴. آزمون REST API

### عمومی

- draft: عدم حضور؛
- publish ولی `needs_review`: عدم حضور؛
- approved ولی draft: عدم حضور؛
- approved + publish: حضور؛
- meta داخلی: عدم حضور؛
- random و related: فقط موارد مجاز.

### نوشتنی

- payload نامعتبر feedback: خطای 400؛
- rate-limit: پاسخ کنترل‌شده؛
- `user_id` جعلی در favorite: نادیده گرفته شود؛
- کاربر فاقد مجوز: 403؛
- همه routeهای مدیریتی دارای permission callback باشند.
