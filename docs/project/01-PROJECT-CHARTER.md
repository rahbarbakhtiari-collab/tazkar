## ۱. نام و هویت محصول

- **نام فارسی:** تذکار
- **نام کاری انگلیسی:** Tazkar
- **نام کاری افزونه:** Tazkar – Quran & Hadith Reflections
- **Slug:** `tazkar`
- **Text Domain:** `tazkar`
- **نویسنده:** رهبر بختیاری
- **مجوز:** `GPL-2.0-or-later`

نام تجاری و آزادبودن نام عمومی پیش از انتشار در WordPress.org دوباره بررسی می‌شود؛ اما Slug و Text Domain در مسیر توسعه ثابت می‌مانند، مگر مانع حقوقی یا مخزنی واقعی اثبات شود.

## ۲. تعریف پروژه

تذکار سامانه‌ای برای آماده‌سازی، مدیریت و انتشار تلنگرهای کوتاه، معتبر و تأمل‌برانگیز برگرفته از قرآن کریم و احادیث دارای مأخذ و بررسی است.

نسخه نخست به‌صورت افزونه تخصصی و ماژولار WordPress عرضه می‌شود. افزونه محتوای ساختاریافته تولیدشده در خط بیرونی ChatGPT و Google Sheets را از CSV و سپس XLSX دریافت می‌کند، آن را اعتبارسنجی و به‌صورت Draft وارد WordPress می‌سازد و پس از تأیید انسانی، برای هر محتوا صفحه‌ای مستقل، زیبا، قابل اشتراک‌گذاری و قابل ایندکس ایجاد می‌کند.

## ۳. مسئله و هدف

تذکار باید هم‌زمان سه نیاز را برآورده کند:

1. حفظ اعتبار علمی، متن عربی و مأخذ؛
2. ایجاد تجربه کوتاه، آرام و مناسب موبایل؛
3. فراهم‌کردن خط تولیدی امن، قابل آزمون، قابل بازگشت و توسعه‌پذیر.

هدف اصلی، ایجاد هسته وبی معتبری است که محتوای قرآنی و حدیثی را با فرایندی ساختاریافته دریافت، بررسی، ذخیره و منتشر کند و برای کانال‌های آینده نیز قابل استفاده باشد.

## ۹. اصول محتوایی غیرقابل‌مذاکره

1. هسته رسمی فقط شامل آیات قرآن و احادیث دارای مأخذ و بررسی است.
2. متن عربی توسط هوش مصنوعی یا افزونه اصلاح، بازنویسی یا نرمال‌سازی ذخیره‌ای نمی‌شود.
3. نسخه نرمال‌شده فقط برای مقایسه داخلی و تشخیص تکرار مجاز است.
4. ترجمه و مأخذ فقط در حد اصلاح تایپی، املایی، فاصله‌گذاری و قالب نوشتاری تغییر می‌کنند.
5. بازنویسی معنایی ترجمه بدون تصمیم صریح مدیر پروژه ممنوع است.
6. متن منبع، ترجمه و متن تولیدی از یکدیگر جدا ذخیره می‌شوند.
7. عنوان و تلنگر نباید از دلالت منبع خارج شوند.
8. وعده قطعی، ترس افراطی، خرافه و انتساب ساختگی ممنوع است.
9. انتشار بدون تأیید انسانی مجاز نیست.
10. موارد مشکوک یا کم‌اطمینان منتشر نمی‌شوند.
11. تأیید گروهی فقط پس از نمونه‌برداری انسانی مجاز است.
12. مشاهده خطای بحرانی، تأیید گروهی همان بسته را متوقف می‌کند.

## ۱۰. خط مبنای فنی لازم‌الاجرا

- حداقل PHP: `8.1`؛
- حداقل WordPress: `7.0.2`؛
- نسخه آزمون‌شده فعلی WordPress: `7.0.2`؛
- نسخه‌های Beta و RC وردپرس، از جمله شاخه پیش‌انتشار `7.1`، خط مبنای Production یا حداقل پشتیبانی نیستند؛
- سازگاری با WordPress پایین‌تر از `7.0.2` هدف پروژه نیست؛
- هر افزایش نسخه پایه فقط پس از انتشار نسخه پایدار رسمی و ابتدا با اصلاح اسناد، Issueها، CI و آزمون‌ها انجام می‌شود؛
- رابط اصلی فارسی و RTL است، اما همه رشته‌ها ترجمه‌پذیر و ظاهر LTR سالم است؛
- کد و نام‌گذاری فنی انگلیسی است؛
- HTML عمومی سمت سرور و قابل ایندکس تولید می‌شود؛
- APIهای WordPress و PHP در اولویت‌اند؛
- JavaScript، CSS و فونت مستقیماً از CDN عمومی بارگذاری نمی‌شوند؛
- وابستگی خارجی فقط با توجیه، مجوز مناسب و امکان جایگزینی پذیرفته می‌شود؛
- migration و upgrade امن و idempotent هستند؛
- deactivation داده را حذف نمی‌کند؛
- uninstall به‌صورت پیش‌فرض داده را حفظ می‌کند؛
- حذف کامل فقط با opt-in روشن مدیر مجاز است؛
- Secret، Token و کلید API در کد یا مخزن ثبت نمی‌شوند.

منبع و فرایند کنترل نسخه WordPress در `docs/management/WORDPRESS-VERSION-BASELINE.md` ثبت شده است.

## ۱۱. امنیت و حریم خصوصی

- capability و nonce برای هر عملیات مدیریتی؛

- حداقل‌سازی payload موقت import؛

- عدم Telemetry؛
- ذخیره داده شخصی فقط به‌اندازه ضرورت و همراه با exporter/eraser در صورت نیاز.

## ۱۴. سطح پروژه

پروژه `critical` طبقه‌بندی می‌شود، زیرا شامل محتوای دینی، import گروهی، migration، rollback، انتشار عمومی و داده کاربر است. این سطح به معنی حذف خودمختاری نیست؛ عمق طراحی، آزمون، شواهد و بازبینی امنیتی بیشتر می‌شود.

## ۱۵. معیارهای موفقیت نسخه نخست

- ورود حداقل یک فایل واقعی با 50 محتوای معتبر؛
- حفظ دقیق متن عربی در تمام فرایند؛
- شناسایی ردیف ناقص، نامعتبر و تکراری؛
- ورود فقط به Draft؛

- rollback امن و محدود به batch؛
- تأیید تکی و گروهی با کنترل خطای بحرانی؛
- انتشار 50 تا 150 محتوای تأییدشده؛
- نمایش صحیح موبایل و دسکتاپ؛
- صفحات server-rendered و از نظر فنی قابل ایندکس؛
- عملکرد علاقه‌مندی، بازخورد، اشتراک‌گذاری و محتوای مرتبط؛
- REST API فقط برای محتوای مجاز؛
- نبود نقص امنیتی یا محتوایی بحرانی باز؛
- ZIP قطعی، مستندات هماهنگ و آزمون RC موفق.

## ۱۶. معیار خاتمه MVP

MVP زمانی خاتمه می‌یابد که:

1. همه اسناد مرجع با نسخه تحویلی هماهنگ باشند؛
2. یک چرخه واقعی Google Sheets تا انتشار کامل شود؛
3. نصب، فعال‌سازی، upgrade، deactivation و uninstall آزموده شوند؛
4. معیارهای پذیرش فنی، امنیتی، محتوایی و کاربری موفق باشند؛
5. نسخه پشتیبان و بازگشت آزمایش شده باشد؛
6. Release Candidate در محیط واقعی یا staging معتبر آزموده شود؛
7. خطاهای بحرانی رفع شوند؛
8. تصمیم انتشار عمومی یا اصلاح اساسی بر پایه شواهد گرفته شود.
